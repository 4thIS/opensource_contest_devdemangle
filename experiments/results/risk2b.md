## 왜 다시 쟀나

risk2에서 방식 2(`⟦0⟧`)가 0%였을 때 원인을 "특수문자를 썼기 때문"이라고 결론지었는데,
그렇다면 **모델이 아는 흔한 기호(따옴표, 언더바)로 감싸면 통과하지 않겠는가**라는 물음이 남았다.
이걸 확인하지 않으면 "왜 하필 그 방식인가"에 답할 수 없다.

두 계열로 나눠 쟀다.

- **계열 A (감싸기):** 용어를 그대로 두고 앞뒤에 표식만 붙인다. 통하면 치환·복원 로직이 통째로 불필요해진다
- **계열 B (치환):** 용어를 다른 토큰으로 바꿔 번역한 뒤 되돌린다

**결론: risk2의 방식 3 채택은 유지된다. 표식을 덧붙이면 오히려 무너진다.**

## ⭐ 핵심 발견 — 생존을 결정하는 건 기호가 아니라 대소문자다

`TERMZERO`(100%)에 표식만 덧붙인 `__TERMZERO__`와 `"TERMZERO"`가 **둘 다 0%로 떨어졌다.**
같은 플레이스홀더인데 감싸기만 추가했는데 100%p가 날아갔다.

출력을 보면 원인이 분명하다.

```
방식 8 입력:  "TERMZERO" 컨테이너를 재시작했습니다
방식 8 출력:  We've restarted the "TerMZERO" container.
                                   ^^^^^^^^  TERMZERO → TerMZERO
```

**플레이스홀더는 자리를 지켰다. 깨진 건 대소문자다.** 표식이 붙으면 토크나이저의 분해 방식이
바뀌고(`▁T`로 시작하던 것이 `"` 뒤의 `T`가 된다), 모델이 그 덩어리를 "복사할 약어"가 아니라
"손봐도 되는 단어"로 취급한다.

같은 현상이 방식 9에서 더 극적으로 나온다. 소문자를 섞었을 뿐인데 플레이스홀더 자체가 번역돼버린다.

```
Termzero  →  DurmZero / HermZero / FermZero / PermZero
```

| 표식 | 토크나이저 분해 | 생존율 |
|---|---|---|
| `TERMZERO` | `['▁T', 'ER', 'M', 'Z', 'ER', 'O']` | **100%** |
| `Termzero` | `['▁T', 'er', 'm', 'z', 'er', 'o']` | 15.4% |
| `"TERMZERO"` | `['▁"', 'T', 'ER', 'M', 'Z', 'ER', 'O', '"']` | 0% |
| `__TERMZERO__` | `['▁_', '_', 'T', 'ER', 'M', 'Z', 'ER', 'O', '_', '_']` | 0% |

6조각으로 쪼개지는데도 100%가 나온다는 게 중요하다. **토큰이 몇 개로 쪼개지느냐는 상관없다.
전부 대문자냐가 상관있다.** 대문자 덩어리는 모델이 약어·고유명사로 보고 그대로 복사한다.

## 방식 2의 원인 — risk2 기록을 정정한다

risk2에서 "어휘에 `⟦`가 없어 unknown으로 떨어진다"고 적었는데 **틀렸다.**

```
⟦0⟧  →  ['▁', '⟦', '0', '⟧']     ← UNK 아님. 어휘에 있다
```

어휘에는 있지만 **학습 코퍼스에 거의 등장하지 않아 모델이 무시한다.** 그래서 기호는 사라지고
의미를 가진 숫자 `0`만 남아 `zero`로 번역된 것이다. risk2.md에 정정 표기를 넣었다.

## 계열 A(감싸기)는 왜 실패했나

따옴표로 감싸는 방식(4번, 69.2%)은 아무것도 안 하는 것(30.8%)보다 두 배 이상 낫다.
따옴표가 "이건 인용이니 건드리지 말라"는 약한 신호로 작동한다. 하지만 충분하지 않다.

```
"TypeScript"     →  "TypheScript"      (음차 변형)
"git commit"     →  "Git company"      (오번역)
"kubectl apply"  →  "kiubectl imply"   (음차 변형)
```

**용어를 원문 그대로 두는 한 모델은 그걸 번역 대상으로 본다.** 표식은 힌트일 뿐 강제가 아니다.
게다가 잔여 따옴표가 12개 남아 후처리가 필요하고, 원문에 따옴표가 있으면 충돌한다.

언더바 방식(5번)에서는 예상 못 한 게 튀어나왔다.

```
_get commit_ and _BAR_push_
                 ^^^^^
```

`_BAR_`는 OPUS 코퍼스에 남아 있던 마크업 잔재로 보인다. 학습 데이터에 이런 플레이스홀더가
섞여 있었고, 언더바를 보면 모델이 그 패턴을 흉내 낸다. **언더바 계열은 쓰지 않는다.**

## 용어 보호 모듈을 만들 때 반영할 것

1. **플레이스홀더는 순수 대문자 영문. 표식을 덧붙이지 않는다.** `TERMZERO` 형태 확정
2. **복원은 대소문자 무시 매칭으로 한다.** 방식 8에서 보듯 플레이스홀더는 살아남고도
   대소문자가 깨질 수 있다. 방식 3이 이번에 100%였던 건 10문장 표본에서 운이 좋았을 가능성이
   있으므로, **정확 매칭에 의존하면 안 된다.** 복원 실패 시 원문 용어를 되살리는 폴백도 둔다
3. **플레이스홀더는 인덱스로 생성한다.** 고정 리스트 5개는 용어가 6개 넘으면 IndexError
   (risk2b 스크립트에서 이미 수정)
4. 대문자화 부작용(`npm install FIRST`)은 **감수한다.** 소문자로 바꾸면 생존율이 무너진다

## 한계

- 표본이 문장 10개·용어 13개다. 이후 픽스처 100개로 재측정한다
- 방식 7·8의 0%는 "플레이스홀더 소실"이 아니라 **"정확 매칭 복원 실패"**다.
  대소문자 무시로 복원했다면 상당수 살렸을 것이다. 이 수치를 "표식을 붙이면 용어가 사라진다"로
  읽으면 안 된다 — 정확히는 **"표식을 붙이면 복원이 불안정해진다"**이다
- 한→영 단방향만 쟀다. 영→한은 별도 측정이 필요하다

## 발표에서 쓸 수 있는 것

"특수문자로 감싸면 되지 않나요?" / "왜 하필 대문자인가요?"에 대해 **9가지를 다 재보고 골랐다**고
답할 수 있다. 특히 "표식을 붙였더니 100%가 0%가 됐다"는 반직관적 결과와 그 원인(토큰 경계 변화 →
대소문자 파괴)은 실측 없이는 나올 수 없는 이야기다.
